PART 1: TRACING AN EXISTING CONNECTOR

Connector chosen: SharePointConnector

1. Where it implements the interface:
   It implements ConnectorInterface with methods:
   authenticate(), list_sources(), fetch(), normalize()

2. Where it registers itself:
   It uses the @register("sharepoint") decorator.
   Orchestration never imports SharePointConnector directly.
   It only calls get_connector("sharepoint") from the registry.

3. One place a bug could leak into orchestration:
   If SharePointConnector.normalize() returns a Document with a missing field,
   orchestration might fail when it tries to read that field.

4. Which of the five steps that gap falls under:
   Step 5: Test success, failure, and partial failure.
   Better tests on normalize() would catch this before it leaks.

PART 2: SKETCHING A SLACK CONNECTOR

authenticate():
  A Slack app uses OAuth 2.0.
  The connector would redirect the user to Slack's authorization page,
  receive a code, and exchange it for a bot token.
  That token is stored and used for all API calls.

list_sources():
  Returns a list of channels the bot has access to.
  Each SourceRef would contain the channel ID and name.

fetch(item):
  Given a channel ID, it fetches recent messages.
  Returns a RawItem containing the message text and metadata.

normalize(item):
  Maps Slack-specific fields to the platform's Document format:
    sender    -> author
    timestamp -> created_at
    thread    -> thread_id
    body      -> content

Would this require touching orchestration code?
  No. Orchestration only calls the four interface methods.
  As long as SlackConnector implements them correctly,
  no orchestration code needs to change.
  If something is missing, that's a sign the interface itself
  needs to be extended - not the connector.
